# Why NVE?

Cross-platform UI toolkits force an uncomfortable trade-off between **native platform fidelity**, **runtime efficiency**, and **developer iteration speed**. Native View Engine (`nve`) resolves this triangle by collapsing the boundary between declarative application logic and platform rendering into one flat binary IR.

## The Problem With Traditional Cross-Platform Bridges

### 1. Per-Prop FFI & JS VM Tax (React Native)

React Native renders real native views (`UIView`, `android.view.View`), which gives unmatched OS text editing, IME, VoiceOver/TalkBack, and scroll physics. However, standard React Native executes reconciliation in Hermes/JSC, allocates JS shadow objects, converts props across JSI into `folly::dynamic` maps, and runs string-key `RawProps` lookups in C++ Fabric.

NVE keeps **React Native's real C++20 Fabric and Yoga engines** — and deletes the JavaScript VM entirely:

- `UIManager` boots with a no-op `RuntimeExecutor` and `startEmptySurface` (**0 ms** Hermes startup, **0 MB** JS heap).
- Native events are intercepted via `EventDispatcher::addListener` and written directly into a compact binary `EventRing` (or zero-copy `NveEventBatch`) using a lightweight recording `jsi::Runtime` subclass for third-party RN components whose payloads only implement `asJSIValue(jsi::Runtime&)`.
- Mutations cross once per frame as a flat `NVE1` `CommandBuffer` instead of thousands of per-prop JSI calls.

### 2. Pixel-Owned Canvas vs. Real Native Views (Flutter)

Flutter achieves consistent 120fps rendering by drawing every widget onto its own Impeller/Skia canvas, but re-implements native scroll physics, platform accessibility semantics, desktop menus, and native controls from scratch — and embeds native views via expensive `PlatformView` synchronization.

NVE lets you pick **real platform-native views** (`AppKit`, `UIKit`, `Win32/Direct2D`, `GTK4`, `Qt 6`, `Android`, `Web DOM`) *or* **direct GPU Skia / Impeller canvases** from the exact same `NveApp` binary. You can even embed an NVE surface inside an existing Flutter app on Flutter's own `Canvas` via `NveCanvasView` + `dart:ffi` with zero `PlatformView` overhead, or embed a native `<Island>` inside an NVE view tree.

### 3. Browser Process Overhead (Electron / WebView Shells)

Electron bundles Chromium and Node.js per application, paying 150–300 MB baseline RSS and hundreds of milliseconds of cold-start latency before the first frame paints.

NVE compiles native apps directly to platform machine code (`~15 MB` class binaries, `< 40 MB` RSS) and supports `MmapSnapshot` Frame-0 boot (`29 µs` raw `mmap` open, `82–136 µs` Frame-0 + state restore for 100 rows). When you *do* want a browser share link or static site, the same Rust crate compiles to a **285.8 KiB gzipped** `wasm-release` bundle with pre-rendered semantic HTML5 SSR and progressive island hydration.

| **Host Bridge Transport** | 1 batched binary `NVE1` buffer / frame + 64B `NveSceneView` | JSI + `RawProps` + `folly::dynamic` | Dart FFI / MethodChannel | IPC + DOM serialization |
| **Real Native OS Views** | Yes (AppKit, UIKit, Win32/RNW, GTK4, Qt, Android, DOM) | Yes (iOS/Android/macOS/Windows) | No (canvas-drawn; `PlatformView` for native) | No (HTML/CSS only) |
| **GPU Canvas Option** | Yes (Skia Metal/Vulkan/D3D12, Qt Quick, `NVE_DRAW1`) | Separate library (`react-native-skia`) | Always Impeller/Skia | WebGL / Canvas2D |
| **Cold Start (Frame 0)** | **82–136 µs** (`MmapSnapshot` Frame-0 replay) | ~150–400 ms (Hermes + JS bundle eval) | ~100–300 ms (Dart VM + engine init) | ~400–1,200 ms (multi-process) |
| **Incremental 10-Node Patch** | **7.12 µs** (C++20 Fabric) / **1.22 µs** (Web DOM) | ~0.5–2.0 ms (JS reconciler + JSI) | ~0.2–1.0 ms (Dart widget rebuild) | ~0.5–3.0 ms (VDOM + Blink) |

## Design Invariants

Every crate in `native-view-engine` obeys four non-negotiable engineering invariants:

1. **Direct typed memory on FFI boundaries, compact binary on wire** — In-process FFI uses direct `#[repr(C)]` structs and slices (`NveDirectEvent` / `NveEventBatch`, `NveMapEntry`, `NveSceneView`, 64-byte `NveNodeMeta`) with zero serialization; network and disk persistence use compact binary codecs (`NVE1` commands, `nve-wire-core`, `NVERELOC`, `MmapOffsetArena`) with bounds checks and `XXH64`/FNV-1a64 integrity hashes.
2. **Framework-agnostic engine core** — `nve-engine` has zero dependency on `dioxus-core`. Dioxus (`nve-dioxus`) is an adapter, not a hard requirement.
3. **Single source of truth for ABIs** — Core and Scene ABIs are derived directly from Rust `#[derive(NveAbi)]` descriptors in `packages/core/abi`, locked by compile-time `offset_of!` assertions and 64-bit FNV-1a schema hashes (`0x053543B32C5D959C` and `0x6D45E53E0D9535D1`), and verified in CI via `cargo nve codegen abi --check`.
4. **Honest verification over smoke tests** — Every decoder and host boundary ships with truncated-buffer, fuzz/property, layout-parity, and state-preservation tests alongside Criterion and C++ statistical regression baselines.
